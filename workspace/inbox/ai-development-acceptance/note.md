AI 辅助开发的方案约束与分层验收，是由人先明确整体设计和改动边界，将约定范围内的实现与测试交给 AI，再从实际行为开始验收，根据发现的问题逐层深入到实现。

## 1. 一个剧情分支需求

例如，要增加一段剧情：玩家持有至少 3 朵花时进入成功分支，数量不足时进入提示分支，两条分支结束后回到共同的后续剧情。

这次开发既要完成分支行为，也要让验收者能够方便地确认数量判断、分支选择和后续衔接是否正确。

## 2. 开发前的方案约束

人先与 AI 明确实现方案，把方向性的判断放在动手之前：

| 约定内容 | 本例中的具体约定 |
| --- | --- |
| 业务语义 | 判断当前背包持有量，已有物品也计入 |
| 实现方式 | 沿用现有的状态读取、条件分支和子段落汇合机制 |
| 改动范围 | 增加剧情配置与测试场景，保持已有节点语义和对外接口 |
| 验收样例 | 分别以 2 朵、3 朵花进入；检查提示分支、成功分支及各自的汇合结果 |

方案确认后，AI 执行具体配置、编码、测试与修复。这里对 AI 的信任落在“按已明确的方案完成边界内工作”，人主要负责整体设计、方案纠正和范围控制。

## 3. 将需求做成可重复的测试场景

准备一个短测试剧本，让玩家可以直接进入数量判断，成功、失败和汇合处都有明确可见的台词；通过已有 GM 工具准备背包和初始位置，再实际操作游戏走过各条路径。

AI 完成操作、录屏、关键截图和状态核对，将明显问题修复后重新测试。这个场景保留下来，后续修改分支、背包或读档逻辑时可以复用，省去重复走完整游戏流程的准备成本。

## 4. 从行为结果逐层深入验收

验收先看实机视频，快速判断是否实现预期；发现疑点时，再沿同一场景向下查看证据。

| 层次 | 本例中检查的内容 |
| --- | --- |
| 视频与关键画面 | 2 朵进入提示分支，3 朵进入成功分支，两条路径都能继续 |
| 步骤截图与操作上下文 | 异常发生前选了什么、背包里有几朵花、前后画面是什么 |
| 节点与运行状态 | 当前执行在哪个节点，读取到的数量和选中的分支是什么 |
| 执行日志 | 状态读取、条件判定、分支跳转和返回分别发生了什么 |
| 配置与代码 | 定位错误的条件、引用或实现逻辑，分析原因 |

例如录像里看到“只有 2 朵花却进入成功分支”，先查看判断前的背包截图，再核对节点读取的数量：若读成了 3，就追查状态读取；若读到 2 仍走成功分支，就追查条件和路由。

每向下一层，都需要理解更多上下文，投入更多精力。对方案明确、范围较小且结果可观察的日常改动，视频中的样例符合预期后即可完成这次行为验收，必要时补充样例；出现疑点或涉及复杂实现时，再深入到代码审查。

## 5. 将报告格式作为协作约定

报告按同一条测试路径组织材料：先交代改动范围和结论，提供可按步骤跳转的视频，再列出“玩家操作、预期结果、实机观察”的截图对照，最后附节点状态、日志、配置与相关代码。

视频保留连续过程，截图方便定位和对照，技术附录承接进一步分析；材料之间能对应到同一个场景和步骤，验收者便可以从发现问题的位置继续追查。

这套方法把人的精力集中在两个地方：开发前控制方案与边界，开发后先以较低成本核对行为，再按需要加深检查；AI 承担范围内的实现、重复测试和证据整理。
