> Web 基础 / 身份认证

**JWT 是一种承载声明的令牌格式；用作签名身份凭证时，它让接收服务能够验证并读取用户身份，减少对集中会话查询的依赖。**

## 解决什么问题

使用 Session 时，订单服务拿到 Session ID，需要查询会话记录才能知道对应用户；多个服务可以共用会话存储来完成查询。

使用签名 JWT 时，登录服务把用户身份和有效期写进凭证，订单服务依据预先建立的信任验证凭证，并从中读取身份信息。

下面采用公私钥签名：登录服务保管私钥，订单服务事先信任登录服务的公钥。

## ① 登录服务生成凭证

用户提交账号密码，登录服务验证成功后，为用户 123 生成载荷：

```json
{
  "sub": "user-123",
  "iss": "https://login.example.com",
  "aud": "order-service",
  "exp": 1893456000
}
```

- `sub`：代表哪个用户。
- `iss`：由谁签发。
- `aud`：凭证面向哪个服务。
- `exp`：到期时间，采用 Unix 时间戳。

再准备头部，描述签名方式和令牌类型：

```json
{
  "alg": "RS256",
  "typ": "JWT"
}
```

`RS256` 表示采用 RSA 签名与 SHA-256 哈希；`JWT` 是令牌类型标记。

登录服务将头部和载荷分别进行 Base64URL 编码，用自己的私钥对“编码后的头部.编码后的载荷”签名，再把签名编码，拼成三段字符串：

```text
编码后的头部.编码后的载荷.编码后的签名
```

## ② 浏览器携带凭证

登录服务把完整 JWT 返回浏览器；浏览器调用订单接口时，将它放进请求头：

```http
GET /orders HTTP/1.1
Host: api.example.com
Authorization: Bearer <完整JWT字符串>

```

## ③ 订单服务验证凭证

订单服务按事先配置的允许算法，使用受信任的登录服务公钥验证签名，并检查签发者、适用服务和有效期。

验证通过后，订单服务读取 `sub=user-123`，将请求关联到这个用户，再根据业务权限返回其有权查看的订单。

## 编码、签名与 HTTPS 的分工

- **Base64URL 编码**：把数据表示为便于传输的字符串，头部和载荷可以解码查看。
- **数字签名**：验证签发来源和内容完整性，用户修改身份字段后，原签名就无法通过验证。
- **HTTPS 加密**：保护 JWT 及其他请求、响应内容在传输途中的机密性和完整性。
