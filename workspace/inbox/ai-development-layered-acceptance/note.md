分层验收通过让 Agent 交付直观、可追查的运行结果，降低人获取验证信息和判断结果的成本，使改动能够更频繁地得到验证。

## 工作流前提：Agent 自主操作与录屏

这套工作流需要 Agent 具备操作应用、执行测试流程和录屏取证的能力；对于游戏，包括完成测试所需的连续操作，并采集关键截图、状态与日志。录屏和这些材料由 Agent 在测试过程中生成，再交给人验收。

开发前由人和 AI 确定方案、改动范围与预期行为；实现后由 Agent 自主运行测试、检查结果，修复明显问题后重新测试并生成验收材料。

## 分层呈现验收信息

人的审查精力有限，不同材料的阅读成本与能回答的问题也不同，因此按以下层次组织验收材料：

| 层次 | 材料 | 主要回答的问题 |
|---|---|---|
| 运行结果 | 录屏 | 实际操作能否完成，行为与体验是否符合预期 |
| 关键步骤 | 截图、操作前后的状态 | 问题从哪一步开始，当时的条件是什么 |
| 执行过程 | 日志、调用与状态变化记录 | 系统实际走了什么路径，在哪个环节偏离预期 |
| 具体实现 | 代码与配置 | 为什么会出现这个行为，应该怎样修改 |

录屏保留连续过程，便于直接判断功能是否正常；截图固定关键时刻，便于快速定位和比较，两者承担不同的阅读任务。

**检查深度由尚未解决的疑问决定。** 对范围明确、行为容易观察的小改动，观看录屏、必要时补充几个测试样例，就能完成验收；发现异常后，再沿着对应步骤查看状态、日志和代码。

报告先呈现结果，再提供可追溯到同一次执行的细节，让人能够逐层深入。

这套方式的收益在于：**大多数常规改动可以在较浅的层次完成验收，人的精力集中到确实需要进一步判断的部分。**
