任务状态与进度管理，是记录任务的执行阶段和目标进度，并根据游戏状态或事件判断任务何时完成。

## 1. 先描述一个最简单的任务

村民要求玩家：接取任务后采集 3 次花，完成后继续对话。

把这句话拆开，就是：

- **何时开始计数**：玩家接取任务后。
- **什么行为计入进度**：采集花，每次计为 1 次。
- **何时达成目标**：累计达到 3 次。
- **达成后做什么**：任务完成，通知剧情继续。

此时只需要保存“已经采集了几次”，每次采花后更新它，再检查是否达到目标。

## 2. 区分接取前后与完成之后：引入任务状态

玩家接取前采的花不计入这次任务；接取后开始累计，达到 3 次完成，之后的采花不再推进它。

因此，除了“已经采集几次”，还需要记录任务处于“未接取、进行中、已完成”中的哪一阶段；只有进行中的任务接受进度更新。

任务状态按“未接取 → 接取后进行中 → 达到目标后已完成”流转，完成时发出一次通知，让剧情继续。

## 3. 增加其他任务：把共同流程与变化的规则分开

现在又有一个“接取后采集 5 次矿石”的任务：

| 任务 | 计入的行为 | 对象 | 达成数量 |
| --- | --- | --- | --- |
| 采花 | 采集 | 花 | 3 次 |
| 采矿 | 采集 | 矿石 | 5 次 |

两者都遵循“接取 → 匹配行为 → 更新进度 → 判断完成”，变化的是对象与数量，这些差异可以提取为任务配置，由同一套任务管理逻辑执行。

如果目标改成“当前持有 3 朵花”，判断方式也发生了变化：

| 目标 | 接取时 | 后续更新 |
| --- | --- | --- |
| 接取后采集 3 次花 | 从 0 次开始 | 每次采花使进度加 1 |
| 当前持有 3 朵花 | 读取已有数量 | 背包变化后重新读取数量 |

因此，配置还需要表达目标的判断类型：是累计行为次数，还是检查当前状态。

## 4. 允许重复接取：分开任务规则与本次执行

同一个任务明天可以再次接取，“采花 3 次”的规则沿用，但这次的进度重新开始。

于是分为两份数据：**任务定义**保存目标规则，**运行实例**保存本次状态和进度；每次接取有独立标识，完成通知据此关联到等待这次任务的剧情。

## 5. 将上述信息展开为 JSON

用自然语言表示：**采花任务，接取后累计采集花的次数，达到 3 次完成；这次任务正在进行，已采集 2 次。**

任务定义把“按什么方式判断、关注什么行为和对象、目标是多少”写成明确字段：

```json
{
  "questId": "gather-flowers",
  "objective": {
    "type": "eventCount",
    "event": "gather",
    "targetId": "flower",
    "required": 3
  }
}
```

其中 eventCount 表示累计事件次数，gather 表示采集行为，flower 表示花，required 表示目标次数。

本次执行的状态和进度单独保存：

```json
{
  "instanceId": "quest-run-42",
  "questId": "gather-flowers",
  "state": "active",
  "current": 2
}
```

questId 关联任务定义，instanceId 标识本次接取，active 表示进行中，current 记录已完成的次数。
