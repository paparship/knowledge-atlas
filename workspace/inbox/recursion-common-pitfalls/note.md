递归通过调用同一个函数来解决更小的子问题。写递归时要分别考虑能否结束、调用会有多深，以及同一个子问题会被算几次。

## 例子：计算任务最早完成的时间

假设任务 A 依赖 B 和 C，B 和 C 可以并行，但两者都要先等 D 完成。A、B、C、D 本身分别耗时 3、2、4、1 秒。箭头表示“依赖”：

```text
A → B → D
A → C → D
```

计算一个任务时，先递归计算各前置任务的完成时间，取其中最晚的时间，再加上自己耗时。没有前置任务时直接返回自身耗时。因此 D 在第 1 秒完成，B 在第 3 秒、C 在第 5 秒完成，A 在第 8 秒完成。

## 1. 递归停不下来

如果误把 D 配成依赖 A，调用就会沿 A → B → D → A 反复绕圈，始终走不到终止条件。把当前递归路径上的任务标为“正在计算”，再次遇到其中任何一个就报告循环依赖。普通递归也遵循同样的原则，每一步都应推进到能直接返回的情况。

## 2. 递归太深，调用栈溢出

如果依赖图是一条很长的链，每层调用都得等下一层返回。即使最后一个任务没有任何依赖，程序也可能在到达它之前耗尽调用栈。可以用循环和显式栈，自己记录待处理任务及处理进度，等前置任务算完再计算当前任务。

## 3. 同一个子问题反复计算

在原例中，计算 B 时算了一次 D，计算 C 时又算了一次 D。依赖图越大，共用的前置任务可能被反复递归计算。第一次算完 D 就缓存它的完成时间，下次直接取结果，这叫记忆化。缓存只记录已经算完的任务，检测循环则看当前路径上正在计算的任务。
