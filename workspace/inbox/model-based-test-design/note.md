建模将需求中的实体关系、状态变化和交互时序明确为结构与规则，形成指导实现、设计测试和审查代码的共同依据。

## 规划时：明确设计，推导测试

自然语言需求通常只说清楚系统要做什么，具体由哪些对象协作、允许哪些状态变化、如何处理调用结果，还需要补充。建模让这些关键判断在代码生成之前得到讨论与确认。

| 建模内容 | 明确的信息 |
|---|---|
| 实体与关系 | 有哪些对象，数据属于谁，对象如何关联 |
| 状态变化 | 有哪些状态，什么条件触发转换，各状态允许什么操作 |
| 交互时序 | 谁调用谁，先后顺序是什么，结果、失败与重复通知如何处理 |

未经测试的代码，其行为是否符合预期处于高度不确定的状态；每增加一次有效测试，就获得一份关于代码实际行为的证据，减少我们对这段代码的不确定性，可以把这个过程理解为“熵减”。**模型将预期行为明确下来，使测试用例能够沿着规则系统地推导。**

例如，需求是“玩家接取任务后采集三次花即可完成”：

| 模型中的规则 | 对应测试 |
|---|---|
| 每个玩家拥有自己的任务进度 | 玩家 A 采集后，玩家 B 的进度保持不变 |
| 只有进行中的任务累计采集次数 | 接取前和完成后采集，任务进度保持不变 |
| 累计到三次，转为已完成 | 两次时仍进行中，第三次转为已完成 |
| 同一次采集事件只处理一次 | 重复收到同一事件，进度只增加一次 |

AI 根据模型实现功能，并通过这些测试获得修正反馈；人则在规划阶段完成对关键结构与规则的理解。

## Review 时：理解结构，检查实现

写代码是从需求出发，逐步推导出设计与实现；审查代码则需要反向理解：这段代码为何存在、对应什么需求、为什么这样组织。局部代码 diff 缺少整体结构，审查者还需要补齐改动与其他模块之间的关系。

**模型保留了这层设计信息，让审查者先理解整体，再检查代码是否遵循设计。**

沿用任务的例子，模型确定任务系统负责进度与状态、采集系统提供事件、界面订阅状态变化；Review 时便可以沿着这些关系检查：计数逻辑是否归属于任务系统、完成通知是否在状态转换时发出、界面是否只根据任务状态更新。

同一份模型在规划时表达预期设计，在审查时提供理解与核对实现的依据，减少反复从代码中还原设计的成本。
