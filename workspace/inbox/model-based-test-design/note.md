未经测试的代码，其行为是否符合预期处于高度不确定的状态；每增加一次有效测试，就获得一份关于代码实际行为的证据，减少我们对这段代码的不确定性，可以把这个过程理解为“熵减”。

## 从需求到模型

要系统地设计测试用例，需要先明确代码应当遵循哪些规则。自然语言需求通常只说清楚系统要做什么，实体关系、交互时序和状态变化等信息还没有展开。

**建模把这些信息补充为明确的结构与规则，让测试用例有依据可循。**

| 建模方式 | 明确的信息 | 推导测试的方向 |
|---|---|---|
| 实体与关系建模 | 有哪些对象，数据属于谁，对象如何关联 | 数据是否正确关联，不同对象之间是否相互影响 |
| 时序建模 | 对象如何调用，操作顺序与结果如何处理 | 不同执行顺序、失败与重复通知时的行为 |
| 状态建模 | 有哪些状态，什么条件触发转换 | 各状态下的操作，以及转换条件的边界 |

## 从模型到测试用例

需求是“玩家接取任务后采集三次花即可完成”，可以先明确以下模型，再逐项推导测试：

| 模型中的规则 | 对应测试 |
|---|---|
| 每个玩家拥有自己的任务进度 | 玩家 A 采集后，玩家 B 的进度保持不变 |
| 任务从未接取进入进行中后，才累计采集次数 | 接取前采集不计数，接取后采集开始计数 |
| 进行中累计到三次，转为已完成 | 采集两次仍进行中，第三次转为已完成 |
| 只有进行中的任务接受进度更新 | 完成后继续采集，任务进度保持不变 |
| 同一次采集事件只处理一次 | 重复收到同一事件，进度只增加一次 |

这些测试可以在实现之前确定，作为 AI 编写代码与自测的共同依据：实现后运行测试，根据失败结果修正，再次验证，形成实现与自测的循环。
