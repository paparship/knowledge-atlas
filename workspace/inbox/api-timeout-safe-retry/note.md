> 后端开发 / 接口可靠性

用户用 100 积分抽奖，接口超时了。后端可能已经扣分并保存了结果，只是响应没回来；此时应沿用原来的 `drawId` 查抽奖流水，拿到原结果或看到「处理中」。

 最小接口

登录用户每次主动发起抽奖前生成一个新的 `drawId`，每次抽奖固定消耗 100 积分，未中奖也算完成。

```text
POST /draws           body: { drawId, activityId }
GET  /draws/{drawId}

两者返回：{ drawId, status, prizeId }
status: PROCESSING | COMPLETED | FAILED
prizeId: 中奖时为奖品 ID，其余情况为 null
```

这类问题要注意的两类设计：
幂等性：
提交抽奖时带上 `drawId`（幂等键）。后端用数据库唯一约束识别同一笔请求，重复提交只返回这笔抽奖的状态或结果，避免再扣一次、再抽一次。
同一次抽奖超时后，用原 `drawId` 查询；若查不到流水，可带原 ID 重提。

事务：
扣分和保存结果能放进同一个本地事务时，就一起提交或一起回滚。如果扣分已单独提交，后端确认抽奖最终失败后，按原扣分流水退回积分，同一笔只退一次。
